## 1. 需求重写公式

把用户原始的、口语化的需求，转换成标准产品语言。

### 公式
```
【场景】 + 【目标用户】 + 【痛点/目标】 + 【成功指标】 = 标准产品需求
```

### 对比示例

| ❌ 原始需求 | ✅ 重写后的产品需求 |
|---|---|
| "我要一个导出Excel按钮" | "用户在每周做汇报的场景下，需要快速把系统里的数据整理成可交付格式，目标是把这个操作从15分钟缩短到1分钟。" |
| "能不能加个暗黑模式" | "晚上使用App的用户觉得屏幕太亮刺眼，我们要提供暗色主题选项，降低夜间使用的视觉疲劳。" |
| "这个审批流程太慢了" | "报销审批流程平均需要5天，导致员工垫付压力大、满意度低，目标是把平均审批时长压缩到2天内。" |

### 重写三原则
1. **不说功能，说问题**：不要写"做一个XX按钮"，写"用户要解决什么问题"
2. **不说主观感受，说可衡量的目标**：不要写"更好用"，写"从15分钟缩短到1分钟"
3. **明确场景和用户**：谁在什么情况下用，不是所有人在所有时候都用

## 2. 投入产出比三角评估

一个需求值不值得做，从三个维度评估：

```
        商业价值
       /        \
      /          \
     /            \
    /              \
   /________________\
用户价值        实现成本
```

### 维度评分（1-5分）

| 维度 | 评分标准 | 5分 | 3分 | 1分 |
|---|---|---|---|---|
| **用户价值** | 多少人受益？受益程度多大？ | 核心功能，所有用户每天都用 | 部分用户每周用几次 | 小众用户偶尔用 |
| **商业价值** | 对收入/留存/成本的贡献 | 直接影响收入或核心留存指标 | 间接影响，需要时间体现 | 几乎没有商业影响 |
| **实现成本** | 需要多少投入？ | 1人天以内 | 5-10人天 | 20人天以上 |

### ROI计算
```
ROI得分 = (用户价值 + 商业价值) ÷ 实现成本
```

**判断标准：**
- ROI > 2：高回报需求，优先做
- ROI 1-2：中等回报，可以做
- ROI < 1：低回报，谨慎投入

## 3. 高回报需求的特征

满足以下3条以上，就是高回报需求：

- ✅ 和产品核心目标强相关（比如你是做效率工具的，提升效率就是核心）
- ✅ 用户面广，不是小众需求
- ✅ 边际成本低（做一次，所有用户都受益）
- ✅ 能带来明显的数据提升（时长/留存/转化/效率）
- ✅ 有网络效应或规模效应
- ✅ 解决的是高频痛点

### 低回报需求的陷阱
- ❌ 只有1个大客户提的，但那个客户特别吵——为他一个人花20人天，其他99个用户不用
- ❌ 看起来很酷，但和产品主线没关系——自嗨型功能
- ❌ 老板个人喜好，不是用户真实需要
- ❌ 做了也没人用，只是"有了总比没有好"

## 4. 创造力三板斧

不是天马行空，而是看到别人没看到的关联。

### 方法一：重新定义问题（Shift the Problem）
> 用户说"我要更快的马"，你不要去养马，你去造汽车。

**练习方式：** 每个需求都问一句——"如果不做这个功能，有没有别的方式能达到同样目的？"

**示例：**
- 需求：用户说"我要一个更复杂的筛选器"
- 重新定义：用户真正的问题是"找不到想要的内容"
- 更优解：智能推荐，而不是让用户自己筛选

### 方法二：跨界迁移
把其他行业的解决方案搬到你的场景里。

**示例：**
- 外卖的"实时配送进度" → 搬到数据产品的"任务执行进度"
- 游戏的"成就系统" → 搬到B端SOP工具的员工激励
- 电商的"购物车" → 搬到企业采购系统的"批量申请"

### 方法三：主动预判下一步
普通PM：用户提了，我做。
优秀PM：用户还没提，我已经把他下一步要做的事准备好了。

**示例：**
- 用户导出Excel之后，下一步通常要发邮件给老板 → 导出成功后直接给个"发送邮件"选项
- 用户上传文件之后，下一步通常要分享给同事 → 上传完成后直接弹出"分享"按钮

## 5. 冲突需求转换：用户分层+可配置

### 什么时候用这个方法？
当你遇到两个**方向相反但都合理**的需求时——比如：
- 有人说"流程太复杂要简化"，有人说"操作太容易误操作要加确认"
- 有人说"消息太多太吵"，有人说"消息太少收不到通知"
- 有人说"首页内容太少"，有人说"首页太乱信息过载"

❌ 错误做法：听A的，B骂街；听B的，A不爽。
✅ 正确思路：不是"二选一"，而是**把选择权还给用户**。

---

### 核心解法：分层 + 可配置

#### 三步法：

**第一步：先搞清楚冲突的根源——是不是不同类型的用户？**

| 冲突表现 | 背后的用户分层 |
|---|---|
| 要简单 vs 要安全 | 新手用户 vs 老手用户 |
| 要多通知 vs 要少打扰 | 活跃用户 vs 潜水用户 |
| 要内容多 vs 要界面干净 | 深度用户 vs 轻度用户 |
| 要两级审批 vs 要五级审批 | 小客户 vs 大客户 |

> 关键判断：如果两个需求来自不同类型的用户，那它们不是"对错之争"，而是"需求不同"。

**第二步：默认值给多数派，选择权给少数派**

- 新用户/新手：默认用"安全模式"（多确认、多引导）
- 用熟了之后：用户可以自己去设置里改成"效率模式"
- 原则：默认值要保守，不要让新手踩坑；但老手必须有得选

**第三步：做"可配置"，不要做"定制开发"**

| ❌ 错误做法 | ✅ 正确做法 |
|---|---|
| 给客户A单独写死三级审批 | 做审批流配置器，客户自己设几级 |
| 给用户A单独关确认弹窗 | 做全局设置开关，所有用户都能自己改 |
| 给VIP用户单独做个首页 | 做首页布局选项，用户自己选精简版/丰富版 |

---

### 典型案例：删除按钮要不要加确认弹窗？

**冲突：**
- 新手："我手滑删了重要数据！要加确认弹窗！"
- 老手："我一天删几百条！每次都弹窗太烦了！能不能关掉？"

**解法：**
1. 默认开启确认弹窗（保护新手）
2. 设置页加一个开关：「删除前确认」（老手自己关）
3. 再加个"撤销删除"（就算手滑了也能找回来）

**效果：**
- 新手不怕误删了
- 老手可以一键关闭提升效率
- 产品不用听两边吵架

---

### 适用场景清单

| 场景 | 冲突 | 可配置解法 |
|---|---|---|
| 操作流程 | 要简单 vs 要安全 | 确认弹窗开关、新手引导开关 |
| 消息通知 | 要多提醒 vs 要少打扰 | 通知分级配置，用户自己选 |
| 界面布局 | 要丰富 vs 要简洁 | 布局模式切换（精简/完整） |
| 审批流程 | 要快 vs 要严谨 | 审批流可视化配置 |
| 字体/显示 | 要大 vs 要小 | 字号调节、主题切换 |

## 6. 方案对比模板

每个需求至少给两个方案对比：

| 对比维度 | 保守方案（MVP） | 创新方案 |
|---|---|---|
| **方案描述** | 最小可用版本，先解决核心问题 | 更优解，从根本上解决问题 |
| **实现成本** | 低（1-2周） | 高（1-2个月） |
| **用户价值** | 解决70%的痛点 | 解决95%的痛点 |
| **风险** | 低，快速验证 | 高，需要更多投入 |
| **适用阶段** | 需求验证期，先跑起来 | 需求确认后，做大做深 |

### 什么时候给创新方案？
- 当保守方案只是"打补丁"，根本问题没解决时
- 当需求已经被验证是真需求，值得长期投入时
- 当竞品都在做保守方案，你有机会做差异化时

## 6. PRD标准结构

转换后的需求，整理成标准PRD条目：

```
【需求名称】一句话说清楚做什么

【背景与场景】
- 什么场景下遇到的问题？
- 现在是怎么解决的？有什么不好？

【目标用户】
- 谁会用这个功能？
- 他们的特征是什么？

【痛点与目标】
- 用户的核心痛点是什么？
- 我们要达成什么目标？（可衡量）

【功能描述】
- 具体要做什么？
- 用户操作路径是什么？

【MVP范围】
- 第一期做什么？
- 哪些先不做？

【成功指标】
- 怎么判断这个需求做成功了？
- 核心数据指标是什么？

【待验证假设】
- 这个分析基于哪些假设？
- 哪些是需要上线后验证的？
```

## B端 vs C端差异提示

| 维度 | B端侧重 | C端侧重 |
|---|---|---|
| 重写重点 | 业务流程、ROI、效率提升 | 用户体验、情绪、使用习惯 |
| 成功指标 | 效率提升、成本降低、转化率 | 留存、时长、NPS |
| 创新方向 | 自动化、流程整合、数据洞察 | 个性化、社交化、游戏化 |
| 方案差异 | 保守=配置化，创新=智能化 | 保守=标准功能，创新=个性化推荐 |

## ✅ 需求转换自检清单

输出分析结果前，逐项检查，缺什么自动补上：

- [ ] 重写后的需求是不是符合"场景+用户+痛点+成功指标"公式？（写得像功能描述=不是产品需求）
- [ ] 有没有算ROI三角（用户价值/商业价值/实现成本）？（没算=不知道值不值得做）
- [ ] 有没有至少给**两个方案**（保守+创新）？（只给一个方案=思路太窄）
- [ ] 成功指标是不是可衡量的？（写"提升体验"=无法验证）
- [ ] 有没有区分"B端侧重"还是"C端侧重"？（没区分=可能判断偏差）
- [ ] 有没有说清楚"哪些先不做"？（没说边界=范围蔓延）
- [ ] 如果有冲突需求，有没有给出"分层+可配置"的解法？（二选一=顾此失彼）

> 检查方式：心里过一遍这7条，哪条没覆盖就自动补到输出里。用户不需要看到这个checklist。
