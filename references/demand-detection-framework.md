---

本框架分别回答：**问题是否成立、采用什么方式处理、是否及何时投入**。真实问题也可以通过修复、引导、配置或人工服务解决；不开发或不符合当前战略，不代表问题是假的。

执行顺序：补全上下文并检查紧急影响与明确约束 → 识别问题与现有能力 → 按需评估证据、价值、成本和不确定性 → 选择处理路径 → 输出结论并决定是否交接。

明确的小缺陷或已有能力满足的使用问题可以简化分析。需新增或系统调整产品能力时，才进入需求转换；证据不足先输出验证计划。多事项竞争资源时可交接优先级排序，简单修复等不必先做完整需求转换。

## 1. 三层挖需与证据判断

用户原话可能是问题，也可能包含方案。信息不清楚时往下挖三层；场景、预期行为和影响已有证据时，不重复追问。

| 层次 | 含义 | 追问示例 |
|---|---|---|
| **表面诉求** | 功能、方案或现象 | 为什么需要这个？ |
| **行为动机** | 要完成的具体任务 | 用它做什么？做完之后呢？ |
| **底层痛点** | 实际障碍、损失或目标 | 不解决会怎样？现在怎么解决？ |

沿任务追问最终目的，区分中间动作与目标。共性能力和业务模型留到转换阶段设计。

### 复合诉求先拆分判断

同一句反馈可能同时包含实际障碍、原因解释和指定方案。先拆成需要核对的判断，分别给证据和成立性结论，再决定整体处理路径；不因其中一句不成立就否定整条反馈，也不因痛点成立就接受用户对原因或方案的判断。拆出的判断不自动视为多个独立需求参与排序。

例如「系统没有批量核销，逐条操作太慢，要新增按钮」：若任务记录支持耗时问题，但已确认现有批量功能能够完成同一任务，则「功能缺失」当前证据不支持，「此前操作负担」已证实；再检查入口、权限或操作方式，不重复开发。结论只覆盖已核对的用户和任务。

### 证据类型与适用范围

根据已有信息简要标注来源、证据类型、涉及的用户/任务及时间或版本范围；缺项写未知，不为补齐表格强制索取与判断无关的信息。

| 证据类型 | 可支持的判断与边界 |
|---|---|
| 用户陈述或访谈 | 支持该用户表达的体验、目标和做法；发生次数、损失和原因解释是否已核对需另行说明 |
| 行为、日志或业务记录 | 支持记录范围内发生的行为与结果；注意样本、时间窗口和缺失记录，不直接推出根因 |
| 任务观察、复现或验收结果 | 支持被观察或测试的角色、条件、版本下的结论；不能外推所有用户与场景 |
| 分析推断或假设 | 解释已有现象或提出验证方向，明确标注依据及待验证项，不作为已证实事实 |

单个客户的问题成立、群体覆盖成立、原因成立、方案有效是不同判断，分别说明证据边界。未核对的转述不写成独立验证结果；依据用户提供的材料下结论时说明来源，不能宣称已亲自检查。证据矛盾时保留已知差异并给出下一步核对动作，不勉强合成确定结论。

手动、Excel、截图等替代做法是问题可能存在的证据，还需检查实际负担、现有能力和改进收益，不能直接证明需求真实或方案值得开发。没有替代做法不代表问题不存在。

遇到bug，记录触发条件、实际与预期结果、影响范围和原因证据。小改动不等于低风险；表现相似不代表根因相同。疑似共同机制问题可交给转换阶段的问题抽象。

### 真实性参考清单

每项记录「有证据 / 无证据支持 / 未知」，区分事实、推断与假设：

- [ ] 有明确的使用场景
- [ ] 用户已在通过某种方式解决问题
- [ ] 不解决存在实际损失或明确目标无法达成
- [ ] 不止一个用户遇到类似问题
- [ ] 与产品核心目标或定位相关
- [ ] 来自实际使用者，或有实际使用者的证据佐证
- [ ] 能说清谁在什么时候做什么，以及卡在哪里

清单用于找证据缺口，**不再按勾选数量判真伪**。人数和战略相关性影响覆盖与投入，不决定问题是否真实；单客户、低频事项或管理层转述也可能有充分证据。

| 问题结论 | 判断依据 |
|---|---|
| **已证实** | 具体场景、实际障碍或损失有可核对证据，如复现、行为记录、访谈和业务记录相互支持 |
| **待验证** | 关键证据不足或矛盾，说明需要补什么证据 |
| **当前证据不支持** | 证据与所声称的问题不符，明确不支持的范围；缺资料本身不足以得出此结论 |

问题已证实不等于用户指定方案有效，方案可能仍需验证。

## 2. 六个判断维度与前置检查

这些是检查视角，不新增总分，也不要求每项都展开成固定表单。

| 维度 | 核心问题 | 影响 |
|---|---|---|
| **问题与证据清晰度** | 场景、障碍、预期结果是否清楚？证据是否支持？ | 直接处理还是先挖掘、验证 |
| **现有能力适配度** | 已有功能、配置、服务能否完成任务？卡在入口、理解、权限还是功能缺口？ | 引导、体验改进、配置或新增能力 |
| **价值与持续性** | 频次、损失、覆盖如何？一次性还是持续发生？ | 是否值得持续投入 |
| **不确定性与风险** | 问题、价值、方案和实现分别有多大把握？失败是否可逆？ | 验证方法、试点边界及止损方式 |
| **共性与复用范围** | 客户特例还是跨场景稳定重复的能力？证据是什么？ | 标记抽象交接信号，不预设平台方案 |
| **约束与战略适配** | 是否越过明确边界？是否符合定位与当前目标？ | 拒绝当前方案、重定义、延后或正常评估 |

### 前置检查

- **紧急影响**：正在阻断核心流程、造成数据损失或其他重大影响时，先明确必要的止损与修复动作，不等待完整评分，再补证据和长期治理判断。
- **明确约束**：违反已确认的安全、合规或权限边界时，拒绝当前方案或重定义。原始目标可能合理，可寻找满足约束的方式；约束不清标待确认，不凭空推定违规。
- **战略适配**：区分不符合产品定位与不符合本期重点。可建议不投入、延后或外部解决，但不因此判伪；稳定性、缺陷修复等必要维护事项单独考虑。

## 3. 痛点强度评估

需比较价值与投入时，按以下维度评分。直接修复等简单事项可简述影响，并说明不评分的理由。

| 维度 | 权重 | 高（3分） | 中（2分） | 低（1分） |
|---|---|---|---|---|
| **频次** | 40% | 每天发生 | 每周1-2次 | 每月1次或更少 |
| **损失** | 35% | 实际财务损失、核心流程阻断或重大数据影响 | 明显时间浪费、效率下降 | 轻微不便 |
| **覆盖范围** | 25% | >50%目标群体 | 20%-50% | <20% |

频次介于示例之间时说明评分依据。覆盖明确分母和单位；B端可使用客户数，不与个人数混算，不能从反馈条数直接推断全体覆盖率。

**加权总分 = 频次×0.4 + 损失×0.35 + 覆盖×0.25**

- 高痛点：总分 ≥ 2.5
- 中痛点：1.5 ≤ 总分 < 2.5
- 低痛点：总分 < 1.5

未知项不当作低分，不编造数值；必要时给上下界，跨档时保留不确定性。低频重大损失不能被平均分掩盖，按前置检查单独处理。

## 4. 处理成本与风险评估

比较具体处理路径的成本，不把用户指定的大方案当作唯一方案。非开发路径记录人工、配置、工具及持续服务成本，不硬套研发量表。

| 维度 | 高成本（3分） | 中成本（2分） | 低成本（1分） |
|---|---|---|---|
| 开发量 | >20人天 | 5-20人天 | <5人天 |
| 技术复杂度 | 底层架构调整或跨团队协作 | 核心模块修改 | 简单前端或配置修改 |
| 实施影响 | 可能影响主流程稳定性，验证投入大 | 局部影响，验证投入有限 | 已确认影响范围小、易回退 |

**综合成本 = 三个维度平均分**：高成本 ≥ 2.5；中成本为1.5至不足2.5；低成本 < 1.5。说明产品、设计、测试、迁移、上线与维护投入的估算口径。

不确定性与不可接受风险单独记录，不用平均分抵消。改动少但影响支付或权限时，仍需验证和回退；资料不足给区间，不默认独立模块就无风险。

## 5. 四象限与中间档处理

四象限辅助投入判断，不替代证据、约束和路径选择。投入可以是修复、引导、配置或服务，低成本不意味着立即排期。

| 痛点 / 成本 | 低成本 | 中成本 | 高成本 |
|---|---|---|---|
| **高痛点** | 优先有效处理，紧急问题先止损 | 比较替代路径，明确范围后投入 | 先止损或拆分；价值或方案不确定时先实验，不能仅因贵就判断问题未证实 |
| **中痛点** | 收益明确且符合目标时可近期处理 | 核实收益与替代方式，按资源选择小范围交付或验证 | 优先低成本路径；缺少充分收益依据时延后 |
| **低痛点** | 有余量且维护成本可接受时处理 | 通常延后，优先非开发方式 | 通常不投入当前方案，保留重评条件 |

高、低两端保留四象限思路，中间档按对应格处理，不强行压成高或低。估算跨档时说明哪项信息会改变结论。关键客户、重大损失和时间窗口可改变建议，但需给依据。

## 6. 五类危险需求识别

以下用于提醒补证据、防误投入，不是自动拒绝标签。

| 类型 | 特征 | 正确做法 |
|---|---|---|
| **解决方案式需求** | 直接说要什么功能，问题不清 | 倒推任务和损失，先验证问题，不直接沿用方案 |
| **个性化定制需求** | 某客户要求特殊流程或规则 | 比较配置、局部实现和服务方式；有共性证据时交给转换阶段评估抽象 |
| **老板拍脑袋需求** | 来源是管理层，缺少使用或业务证据 | 确认使用者和业务目的，不能只因来源判伪 |
| **竞品跟风需求** | 主要理由是竞品已有 | 检查本产品用户任务与实际缺口，竞品存在不等于价值证明 |
| **临时一次性需求** | 明确的一次性时间窗口 | 比较人工、配置、现成工具，计入重复服务可能性及总成本 |

## 7. 处理路径与后续分流

以下情况可同时出现，不是八选一。先处理紧急影响和明确约束，再选主路径，可安排先止损、再验证或治理。

| 情况与条件 | 建议路径 | 最小输出 / 后续动作 |
|---|---|---|
| **明确的小缺陷**：触发、预期行为和影响清楚 | 直接修复、补验收；高影响先止损 | 复现、预期结果、验收与回归范围；原因或影响不明、涉及共同机制时再分析 |
| **现有能力满足任务，但使用受阻** | 按原因选引导、入口或交互改进、授权流程改进 | 现有能力与阻碍证据；不默认归咎用户，不用培训掩盖设计问题或绕过权限 |
| **特有、低频或一次性事项**，复用收益不足 | 比较人工服务、配置和现成工具 | 交付结果、边界及一次性和持续成本，不必形成功能 |
| **给了方案，但问题不明确** | 先挖掘与验证 | 场景、证据缺口、验证方法与通过条件，暂不完整功能设计 |
| **价值或方案不确定的新需求** | 按风险选实验或MVP | 假设、对象、指标、投入上限和停止条件；线上风险不可控先离线验证 |
| **稳定、高频、多用户的持续需求** | 评估持续能力，必要时模块化 | 持续性与收益证据，检查现有能力；需新增能力才交接转换 |
| **多个业务出现相似能力** | 标记复用候选，交接抽象评估 | 已知场景、共性证据与差异，不直接决定平台化；紧急修复不等待平台建设 |
| **方案触碰明确边界或不符合定位、阶段目标** | 拒绝当前方案、重定义、外部解决或延后 | 区分硬约束与阶段取舍，保留真实性结论，给替代方向或重评条件 |

处理路径与投入时机分开：例如问题已证实，选择现在提供人工服务，但不投入产品功能；也可问题已证实，方案待验证，先实验而非全量开发。

### 是否需要进入需求转换

给出结论及当前依据，不因反馈真实就自动设计功能：

| 结论 | 条件与后续 |
|---|---|
| **无需完整转换** | 已确认问题可由明确修复、已有功能、配置或服务解决，且无需重新设计系统能力；给交付/验收。复杂修复或系统性缺口仍可进入转换 |
| **暂不转换** | 尚不能界定用户任务、值得检验的价值假设或关键约束，或当前方案明确不投入；先补最小证据，区分暂缓和不投入，给重评条件，不直接承诺功能 |
| **需要转换** | 有依据的任务缺口需新增或系统调整能力，且能说明交付目标或可检验的价值假设；进一步明确规则、范围、方案及交付。收益大小或解法未确定时可转换为有限验证方案，不要求先证明全部收益或方案有效 |

紧急事项可先止损再补转换，不能让完整分析阻塞处理。仅要求标准化描述或文档整理时可按用户范围输出，但不据此宣称值得开发。需转换时交接已知事实、关键未知、候选范围与约束；建设形态在转换阶段比较后决定。

## 8. 实验与MVP切割原则

只在需要验证或交付新能力时使用，不对所有问题强制MVP。

### 先区分验证对象

- **问题或价值不确定**：用访谈、任务观察、原型、人工服务或小范围实验验证是否值得解决。允许人工参与，但记录工时、效果、限制和用户知情情况，不宣称已自动化。
- **问题已证实、方案待验证**：检验任务能否完成、结果是否改善。
- **问题与方案均较明确**：切出最小可交付闭环，而非重复验证问题存在。

验证计划包含：假设、对象与场景、方法、指标与通过条件、期限与投入上限、停止或调整条件。未知阈值标待确认，不编造基线。

### MVP切割

1. 保留核心任务和完成结果，删除非必要扩展。
2. 缩短路径，限定人群、场景或规则范围。
3. 按关键假设确定必要质量，不削减安全、权限、数据正确性或核心可靠性。

人工辅助验证可以成立；产品MVP需说明自助范围和人工兜底成本，不能将未完成的自助流程宣传为完整自助产品。1-2周是切割参考，不是所有MVP的硬门槛。

不可逆损失、权限或关键数据等高风险事项，先用原型、模拟或测试环境验证。仅在风险可控、验证与回退边界明确时考虑线上试点，不能以MVP绕过必要质量标准。

## 9. 分辨输出与交接

先输出三类结论，再按需补评分与证据：

| 维度 | 输出要求 |
|---|---|
| **问题是否成立** | 已证实 / 待验证 / 当前证据不支持，注明判断对象、证据类型/来源、适用范围和未知项；复合诉求分别给结论 |
| **采用什么处理方式** | 主路径与理由，必要时说明先后动作，以及现有能力能否承接 |
| **是否及何时投入** | 现在处理 / 先验证 / 延后 / 不投入当前方案，明确投入对象与重评条件 |
| 痛点与成本（按需） | 分项依据、档位或区间；省略评分时说明原因 |
| 约束与风险 | 已知约束、不确定性及需先处理的影响 |
| 下一步与验收 / 验证 | 具体动作、可核对结果或通过条件，未知项标待确认 |
| 后续交接 | 明确需要转换 / 暂不转换 / 无需完整转换及依据；多事项竞争资源进入排序，不要求先设计所有事项 |

旧模板中的「做 / 不做 / MVP / 延后」可作为投入建议的简写，但需保留三类结论，不将做等同于开发。不需要转换的事项，不强制需求重写、抽象模型、保守与创新双方案或PRD。

假设与风险按实际缺口列出，不凑数量虚构问题；信息齐全的简单修复直接给验收和相关回归要求。

## B端 vs C端差异提示

| 维度 | B端侧重 | C端侧重 |
|---|---|---|
| 价值判断 | 流程、业务收益、交付与维护成本 | 任务完成、体验、留存等已知目标 |
| 覆盖范围 | 明确客户数、角色或席位分母，关键客户说明业务影响 | 明确受影响群体与规模，不以反馈条数代替覆盖 |
| 成本与替代方式 | 比较配置、服务与开发的总成本 | 比较自助体验、支持成本和规模化影响 |
| MVP与验证 | 可人工辅助验证，区分验证服务与正式交付 | 关注真实使用和任务完成，不只看口头意愿 |

两类产品均需证据、质量和投入判断，不按类型默认高成本可接受、付费意愿低，或体验比业务影响更重要。

## ✅ 需求分辨自检清单（三层评测）

按路径检查。缺证据时标未知或给验证动作，不强制补造分数和假设。

### 第一层：完整性（有没有漏）
- [ ] 问题、当前做法与现有能力是否清楚？缺证据是否标未知并给补证据动作？
- [ ] 需评分时是否评估频次、损失、覆盖和成本，明确分母、边界与未知项？简单路径省略评分是否说明理由？
- [ ] 是否识别适用的危险需求、紧急影响、明确约束与战略适配？
- [ ] 是否分别给出问题成立性、处理方式、投入时机、转换必要性及下一步动作，未把问题真实或要求写文档等同于批准开发？

### 第二层：质量（做得够不够好）
- [ ] 是否拆分复合诉求并标明证据来源、类型和适用范围，未把局部事实外推为普遍结论，也未用人数、来源、替代做法或战略相关性直接判真伪？
- [ ] 是否解释路径与投入建议，覆盖中间档和替代方案，而非只给象限结论？
- [ ] 适用时是否明确修复验收、引导或服务交付结果、实验通过和停止条件、MVP最小闭环？

### 第三层：反面检查（有没有犯错）
- [ ] 是否把用户方案直接当必做功能、将使用问题归咎用户，或把重复能力直接升级为平台？
- [ ] 是否遗漏低频重大影响、用平均分抵消不可接受风险，或对简单处理强制完整转换、双方案和PRD？

> 共9条，按适用路径检查。不适用项无需生成内容，自检清单不必逐条展示。
