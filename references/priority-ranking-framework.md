## 2. 三大常用排序方法对比

| 方法 | 适用场景 | 优点 | 缺点 |
|---|---|---|---|
| **RICE打分法** | 有数据支撑，需要量化对比 | 客观，可复现 | 需要数据，计算稍复杂 |
| **MoSCoW分类法** | 项目初期，快速分类 | 简单快速 | 太粗，同级别内没法再排 |
| **价值/复杂度矩阵** | 直觉判断，快速决策 | 直观易懂 | 偏主观，不够精确 |

**推荐组合：** 先用MoSCoW分类，再在同一类里用RICE打分排序。

## 2.5 排序前必过的两道关

在打分排序之前，先过这两道关——这是比ROI更重要的判断：

### 第一关：战略对齐

> 这个需求跟产品当前阶段的核心目标是不是一致？

**为什么要先过这关？**
单看ROI都不错的需求堆在一起，资源就那么多，做了这个就做不了那个。如果做了一堆"看起来很赚钱"但跟主线没关系的事，年底复盘会发现：忙了一年，OKR没完成。

**判断问题：**
- 这个需求做完，对今年的核心目标（OKR）有没有直接帮助？
- 是在加深产品主线，还是在开新坑？
- 如果我们现在资源砍一半，这个需求还会做吗？

| 对齐程度 | 处理方式 |
|---|---|
| 高度对齐 | 正常参与排序 |
| 中度对齐 | 往后排，先做主线 |
| 不对齐 | 直接延后/不做，哪怕ROI再高 |

### 第二关：需求冲突

> 做了这个需求，会不会伤害其他用户或其他模块的体验？

**为什么要先过这关？**
有些需求单看很好，但做了会引发新的矛盾——比如简化流程会让老手爽了，但新手容易误操作。

**判断问题：**
- 这个需求有没有相反的用户声音？
- 做了A，B类用户会不会不满意？
- 有没有两全的解法（比如分层、可配置）？

| 冲突程度 | 处理方式 |
|---|---|
| 无冲突 | 正常参与排序 |
| 有冲突但能解决（分层/可配置） | 正常排序，但方案要设计好 |
| 有冲突且没法平衡 | 降低优先级，或者直接放弃 |

## 3. RICE打分法（推荐）

### 公式
```
RICE得分 = (Reach × Impact × Confidence) ÷ Effort
```

### 四个维度

| 维度 | 含义 | 评分方式 |
|---|---|---|
| **Reach（触达）** | 多少人会受影响？ | 每季度受影响的用户数 |
| **Impact（影响）** | 对每个用户的影响有多大？ | 3=巨大, 2=高, 1=中, 0.5=低, 0.25=极小 |
| **Confidence（信心）** | 我们对这个判断有多大把握？ | 100%=高, 80%=中, 50%=低 |
| **Effort（投入）** | 需要多少人月？ | 工程+设计+产品总投入，按月算 |

### 示例计算

| 需求 | Reach（人/季） | Impact | Confidence | Effort（人月） | RICE得分 |
|---|---|---|---|---|---|
| 需求A | 10000 | 2 | 80% | 2 | (10000×2×0.8)÷2 = 8000 |
| 需求B | 50000 | 1 | 100% | 5 | (50000×1×1.0)÷5 = 10000 |
| 需求C | 1000 | 3 | 50% | 1 | (1000×3×0.5)÷1 = 1500 |

**排序结果：** B > A > C

### B端特殊调整
B端产品Reach可以用「付费客户数」代替「用户数」，大客户权重更高。

## 4. MoSCoW分类法

把需求分成四类：

| 类别 | 含义 | 占比建议 |
|---|---|---|
| **Must have（必须做）** | 不做产品就跑不起来，或者会出大问题 | 60% |
| **Should have（应该做）** | 很重要，但不是马上必须，晚点做也行 | 20% |
| **Could have（可以做）** | 锦上添花，有了更好，没有也不影响 | 15% |
| **Won't have（这次不做）** | 这次明确不做，以后再说 | 5% |

### 判断标准

| 类别 | 判断问题 |
|---|---|
| Must | 不做会怎样？会不会导致用户流失/系统崩溃/合规问题？ |
| Should | 做了有什么明显好处？不做有什么明显坏处？ |
| Could | 做了用户会开心吗？不做用户会抱怨吗？ |
| Won't | 这个需求和本期目标相关吗？值得投入吗？ |

## 5. 价值/复杂度矩阵

直观的四象限排序：

```
        高价值
          |
  🟢 优先做    |    🟡 规划做
  （高价值+低复杂度） |  （高价值+高复杂度）
          |
----------+----------
          |
  🔵 顺手做    |    ⚪ 不做
  （低价值+低复杂度） |  （低价值+高复杂度）
          |
        低价值
```

### 排序优先级
1. **第一优先：高价值 + 低复杂度**（ quick win，先拿成果）
2. **第二优先：高价值 + 高复杂度**（重要的事，拆成MVP慢慢做）
3. **第三优先：低价值 + 低复杂度**（有空就做，凑数）
4. **最后考虑：低价值 + 高复杂度**（直接放弃）

## 6. 排序输出模板

当有多个需求时，输出这个排序表：

### 需求优先级排序表

| 排名 | 需求名称 | RICE得分 | MoSCoW分类 | 一句话理由 |
|---|---|---|---|---|
| 1 | | | Must | |
| 2 | | | Must | |
| 3 | | | Should | |
| 4 | | | Should | |
| 5 | | | Could | |
| 6 | | | Won't | |

### 排序原则说明
- **先按MoSCoW大类分**：Must > Should > Could > Won't
- **同一类内按RICE得分排**：分数高的在前
- **特殊情况调整**：如果有强时间窗口（比如要赶某个节点），单独标注说明

## B端 vs C端差异提示

| 维度 | B端侧重 | C端侧重 |
|---|---|---|
| Reach权重 | 付费客户数>普通用户数 | 活跃用户总数 |
| Impact权重 | 对客户业务影响大的权重高 | 对留存/时长影响大的权重高 |
| Confidence | 客户明确提的=高信心 | 需要数据验证的=中低信心 |
| Effort评估 | 跨部门协作成本要算进去 | 主要看研发投入 |
| Must判断 | 合规/系统稳定/核心业务流程 | 核心路径/新用户引导 |

## ✅ 优先级排序自检清单（三层评测）

输出前逐项检查，缺漏自动补，错误自动修正：

### 第一层：完整性（有没有漏）
- [ ] 每个需求有没有量化打分（RICE或MoSCoW）？
- [ ] 每个需求有没有过"战略对齐"这一关？
- [ ] 有没有识别出需求之间的依赖关系？
- [ ] 每个排名有没有写核心理由？（不是只给个名次）

### 第二层：质量（做得够不够好）
- [ ] 打分有没有依据？还是拍脑袋排的？
- [ ] B端需求有没有考虑大客户权重？
- [ ] 有没有至少一个quick win（低成本高价值）？（全是大需求=团队没正反馈）

### 第三层：反面检查（有没有犯错）
- [ ] 有没有只看ROI，忘了战略方向？（做了一堆赚钱但偏离主线的事）
- [ ] 有没有忽略了需求冲突？（做了A会得罪B）
- [ ] 排期是不是 realistic？（一口气排10个大需求=根本做不完）

> 共11条，过一遍大概10秒钟。哪条不过就补哪条。
