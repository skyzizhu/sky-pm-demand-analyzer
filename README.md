# sky-pm-demand-analyzer

> 产品经理需求分析与转换助手：判断问题及处理方式，抽象有边界的产品能力，形成需求草稿，并在证据、依赖与容量约束下比较优先级。

## v1.5.0 更新

- 需求分辨分别输出问题成立性、处理路径和投入时机；支持修复、引导、配置、服务和验证，复合诉求拆分判断，证据限定适用范围。
- 需求转换按需比较方案，允许只有一个有依据的方案；效果与指标注明来源及确认状态。
- 修正投入比较：总投入使用同口径人天，取消成本反向评分和旧ROI绝对阈值。
- 排序先识别必要事项，再检查可选投入的战略与冲突；信心取决于证据，不因客户明确提出自动提高。
- 区分相对价值与实际实施顺序，检查前置、共享投入、容量与角色；无容量不承诺排期，也不强凑quick win。
- 同步10个模拟案例及PRD模板，避免旧示例覆盖新规则。

## 三个核心框架

| 框架 | 回答的问题 | 主要输出 |
|---|---|---|
| **需求分辨** | 问题成立吗？现有能力能否承接？怎么处理、何时投入？ | 证据与未知项、处理路径、投入建议及验收/验证动作 |
| **需求转换** | 新增或系统调整能力时，如何定义问题、抽象与范围？ | 标准需求、按需抽象、方案依据、价值与投入、MVP和指标 |
| **优先级排序** | 多个事项怎样取舍，当前资源能交付什么？ | 必要性与分类、可比时的RICE、依赖、条件化实施建议 |

**整体流程：分辨 → 按需转换 → 多事项按需排序。**

修复、引导、配置或服务可在分辨阶段结束；证据不足先给验证计划；需要新增或系统调整能力才进入转换。用户只请求某环节时按该环节输出，不自动展开完整链路。多事项竞争资源可直接进入排序，不强制每项都写PRD。

## 适用场景与提问示例

| 你说的话 | 处理重点 |
|---|---|
| 「客户说要加导出Excel，帮我判断要不要做」 | 回到任务与现有能力，选择处理路径 |
| 「用户找不到已有功能，要不要再做一个入口」 | 分开判断能力缺失与发现困难 |
| 「客户A要三级审批、B要两级，能不能共用」 | 共性证据、业务模型、配置与能力边界 |
| 「两个场景都出现库存异常，要不要统一治理」 | 分开记录表现和根因证据，不凭相似就合并 |
| 「日报和月报口径对不上，帮我整理」 | 数据粒度、指标口径、层级与追溯 |
| 「只有一个合理方案，也帮我整理成需求」 | 说明选择依据，不强造创新方案 |
| 「剩余0.5人月，这几个事项怎么安排」 | 必要事项、前置与容量检查 |
| 「没有容量数据，先排相对优先级」 | 条件化分类，不承诺具体排期 |

B端、C端均使用证据和任务判断，不按产品类型预设收益、成本或技术方案。

## 需求分辨的处理路径

六个视角是证据清晰度、现有能力、价值与持续性、不确定性与风险、复用范围、约束与战略。它们不组成新的总分。

可选择修复、引导或体验改进、配置或服务、先验证、持续能力建设、复用评估、延后或重定义。情况可重叠，重大影响先止损。痛点、成本按需评分，含中间档；未知保留未知或区间，不按清单勾选数量定真伪。

问题已证实不等于原因、用户指定方案或群体覆盖也已证实。单一客户、少数反馈、管理层提出或不符合本期目标，不构成判伪依据。

## 需求转换与四类抽象

**问题重写 → 按需抽象 → 能力边界 → 方案选择 → 价值与投入 → MVP。**

重写包含场景、目标用户、痛点/目标、成功指标；未知基线、目标或规则标待确认，不照抄示例数字。

| 抽象方式 | 适用问题 | 输出 |
|---|---|---|
| 需求抽象 | 多客户诉求或具体定制 | 共性、差异、复用证据与配置边界 |
| 业务抽象 | 多角色、多对象、复杂流程 | 实体与关系、规则、状态流转 |
| 问题抽象 | 重复bug或跨场景故障 | 分类、根因证据/假设、修复与治理边界 |
| 指标/数据抽象 | 粒度、汇总层级和指标口径 | 数据来源、口径、层级及追溯 |

按场景选择，可组合，不强制四类全做。业务抽象采用「列实体 → 理关系 → 提规则 → 画状态流转」。复用有证据且收益覆盖成本时再考虑通用能力，不默认平台化。

多个合理路径可比较配置、流程、服务、局部开发或通用能力；只有一个合理方案时说明依据。新技术、大范围或差异化本身不证明效果更好。

### 价值与投入比较

`效益投入得分 =（用户价值分 + 商业价值分）÷ 总投入人天`

用户和商业价值按1—5分说明依据，总投入包含产品、设计、工程、测试、配置、迁移、上线及选定周期内维护，非人工成本和风险另列。这是同口径候选方案的启发式比较，不是财务ROI，不使用旧成本分和旧绝对阈值。

数据未知、总投入为零或无法统一口径时不计算；区间重叠不强定排名。本得分不与RICE相加，也不自动决定开发。指标区分已测基线、建议目标和确认目标，并注明来源、人群、时间窗口及测量方式。

## 排序与实施建议

1. 继承分辨证据、未知项及转换的范围和依赖。
2. 先判断正在造成重大损失的故障、必要维护、明确硬性义务与期限，安排最低范围；不因其不直接贡献阶段增长而过滤。
3. 对可选投入检查战略与冲突，再按必要性使用MoSCoW；输入有依据且可比时，在同类内参考RICE。
4. 按前置、共享投入、容量、关键角色和窗口形成实施建议。容量不足明确缺口，无容量则只给相对优先级。

`RICE = Reach × Impact × Confidence ÷ Effort`

Reach统一人群单位及周期，Impact对应同一目标，Effort统一人月及纳入范围；Confidence根据覆盖与效果等证据解释。客户提出不等于高信心，关键估计无依据时不强算。必要事项不靠高分证明必须处理，也不默认资源无限。

价值排名不等于实施顺序。依赖需先完成，共享成本只计一次，覆盖去重；没有quick win可以如实说明，没有可容纳事项可保留余量。实际安排仍需PM确认取舍。

## 输出与质量自检

| 路径 | 输出 |
|---|---|
| 分辨或简单处理 | 三类结论、证据范围、下一步及必要验收/交付要求 |
| 先验证 | 假设、对象、方法、指标与通过条件、期限/投入上限及停止条件 |
| 需求转换 | 需求描述、按需抽象、方案依据、投入、首期范围与指标；需要时使用PRD模板 |
| 多事项排序 | 分类、依据与依赖；已知容量时补本期范围、实施顺序、余量与未安排项 |

假设和风险不固定数量，不为模板凑数。自检帮助发现遗漏与矛盾，不能保证证据真实或自动消除判断误差。

| 框架 | 自检项数 | 层次 |
|---|---|---|
| 需求分辨 | 9 | 完整性 → 质量 → 反面检查 |
| 需求转换 | 14 | 完整性 → 质量 → 反面检查 |
| 优先级排序 | 10 | 完整性 → 质量 → 反面检查 |
