# sky-pm-demand-analyzer

> 产品经理需求分析与转换助手 —— 判断需求真伪，抽象共性与业务模型，界定能力和MVP范围，转换为标准产品需求，并对多个需求排序。

## ✨ 核心能力

| 模块 | 功能 |
|---|---|
| **🔍 需求分辨** | 三层挖需法、最终目标追问、问题证据梳理、真伪判断、痛点强度、四象限、MVP切割与质量自检 |
| **🔄 需求转换** | 需求重写、四类抽象、能力边界、ROI评估、方案对比、PRD结构与质量自检 |
| **📊 优先级排序** | RICE、MoSCoW、价值/复杂度矩阵、共用能力与依赖处理、排序输出与质量自检 |

- 在需求转换中加入需求、业务、问题、指标/数据四类抽象，按场景选择，可组合使用。
- 用「列实体 → 理关系 → 提规则 → 画状态流转」梳理业务，说明共性、差异和能力边界。

## 🎯 适用场景

- 收到用户/老板/业务方提的需求，不知道该不该做
- 不知道怎么把口语化的需求转成标准PRD
- 多个需求堆在一起，不知道先做哪个
- 需要快速判断一个需求是真痛点还是伪需求
- 多个客户提出不同要求，需要识别共性、配置项和不支持的特例
- 业务流程复杂，需要梳理实体、关系、规则和状态变化
- 出现重复bug或报表口径不一致，需要分析共同机制或数据层级
- B端、C端产品经理都能用

## 🚀 使用方式

### 触发方式
直接跟AI助手说需求相关的问题，比如：

| 你说的话 | 触发能力 |
|---|---|
| "帮我分析一下这个需求：用户说要加个导出Excel功能" | 需求分辨 + 转换 |
| "这个需求怎么做MVP？" | 需求分辨 + MVP方案 |
| "把这几个需求排个优先级：xxx、xxx、xxx" | 优先级排序 |
| "这个需求要不要做？" | 需求判断 |
| "帮我把这个用户需求转成产品需求文档" | 需求转换 |
| "客户A要三级审批，客户B要两级审批，怎么抽象成共用能力？" | 需求转换：需求抽象 + 业务抽象 |
| "取消订单和退款后库存都不对，帮我分析是否需要系统治理" | 需求分辨 + 转换：问题抽象，先验证共因 |
| "门店日报和区域月报的数据对不上，帮我梳理数据层级和指标口径" | 需求转换：指标/数据抽象 |

### 执行流程

整体沿用三个框架：**需求分辨 → 需求转换 → 优先级排序**。仅在同时提交多个需求时执行排序。

需求转换按以下顺序进行：

**问题重写 → 按需抽象 → 界定能力边界 → 方案对比 → 价值与成本评估 → MVP范围**

四类抽象的选择方式：

| 抽象方式 | 适用问题 | 主要输出 |
|---|---|---|
| 需求抽象 | 多客户诉求、重复功能、特定定制 | 共性、差异、复用证据和配置边界 |
| 业务抽象 | 多对象、多角色、复杂业务流程 | 实体与关系、规则、状态流转 |
| 问题抽象 | 重复bug、跨场景故障 | 问题分类、根因证据或假设、修复与治理范围 |
| 指标/数据抽象 | 数据粒度、汇总层级、指标口径差异 | 数据来源、口径、层级与追溯关系 |

简单需求可说明无需进一步抽象的理由。共性尚未验证时标注假设；先比较复用收益与配置、迁移、维护成本，再决定是否建设通用能力。指标/数据抽象用于组织与解释数据，成功指标用于判断需求效果，两者可相互引用。

详细规则见[需求转换框架](references/demand-conversion-framework.md)。

### 输出形式
每次分析都会输出**表格化的需求分析卡片**，包含：

1. **需求判断卡片** —— 真伪/痛点/成本/象限/结论
2. **重写后的产品需求描述** —— 用标准产品语言重写
3. **抽象结果与能力边界（按需）** —— 共性、差异、复用依据及适用的业务模型或数据口径；简单需求说明无需进一步抽象的理由
4. **方案对比与MVP范围** —— 保守方案 vs 创新方案、首期范围与验证目标
5. **待验证假设 & 风险** —— 关键假设和潜在风险

## ✅ 内置三层质量自检体系

每个模块输出后，自动跑三层自检，缺漏自动补，错误自动修正：

| 模块 | 自检项数 | 三层结构 |
|---|---|---|
| 需求分辨 | 9条 | 完整性（有没有漏）→ 质量（做得够不够好）→ 反面（有没有犯错） |
| 需求转换 | 14条 | 完整性 → 质量 → 反面 |
| 优先级排序 | 10条 | 完整性 → 质量 → 反面 |

**三层分别查什么：**
- **第一层·完整性**：有没有漏做关键步骤？（比如没挖现状、没算ROI）
- **第二层·质量**：做了，但做得够不够好？（比如痛点判断是拍脑袋还是有依据？）
- **第三层·反面检查**：有没有犯常见错误？（比如把用户方案当成了需求？）

> 自检是自动的，用户不需要看到checklist，只需要看到最终成品。

## 🧭 排序两道关（v1.3.0新增）

打分排序之前，先过这两道关——比ROI更重要：

### 1. 战略对齐
这个需求跟产品当前阶段的核心目标是不是一致？
- 不对齐的需求，ROI再高也往后放
- 避免做了一堆"看起来赚钱"但偏离主线的事

### 2. 需求冲突
做了这个需求，会不会伤害其他用户的体验？
- 先识别冲突类型，再选择分层、配置、场景切换、分期或先验证等方向
- 根据业务证据和资源约束取舍，不预设必须增加配置项

---

## 🔄 冲突需求分析与转换（v1.3.0新增）

遇到方向相反但都合理的需求时，先分析冲突类型，再选对应转换方向：

| 冲突类型 | 特征 | 可选转换方向 |
|---|---|---|
| 用户分层型 | 不同类型用户诉求天然不同 | 分层体验 / 可配置开关 / 分人群灰度 |
| 场景差异型 | 同一用户在不同场景需求相反 | 智能切换 / 手动开关 / 默认值+提醒 |
| 优先级取舍型 | 资源有限只能做一个 | 排期分阶段 / 折中方案 / 版本拆分 |
| 认知偏差型 | 某方需求可能是伪需求 | 先验证 / 做引导 / 优化现有流程 |

> 不预设标准答案，根据具体冲突类型和资源情况选最合适的方向。

## 📐 框架详解

### 需求分辨框架

- **三层挖需法**：表面诉求 → 行为动机 → 底层痛点
- **真伪判断清单**：7个是/否问题，辅助判断需求真实性
- **痛点强度三维度**：频次、损失、覆盖范围，按40%、35%、25%加权求和
- **四象限决策矩阵**：痛点强度 × 实现成本，对应四种处理策略
- **五类危险需求识别**：解决方案式需求、个性化定制、老板拍脑袋、竞品跟风、临时一次性需求
- **MVP切割原则**：砍到能解决80%痛点的最小闭环

### 需求转换框架

- **需求重写公式**：场景 + 用户 + 痛点/目标 + 成功指标
- **需求与业务抽象**：按需选择需求抽象、业务抽象、问题抽象、指标/数据抽象
- **业务抽象方法**：列实体 → 理关系 → 提规则 → 画状态流转
- **抽象边界**：用证据区分共性与差异，比较直接实现和通用能力的收益与成本，不默认平台化
- **ROI三角评估**：（用户价值 + 商业价值）÷ 实现成本，作为启发式比较分数
- **高回报需求特征**：6条判断标准
- **创造力三板斧**：重新定义问题、跨界迁移、主动预判下一步
- **方案对比模板**：保守方案 vs 创新方案的6维度对比
- **PRD标准结构**：背景、目标用户、痛点与目标、功能描述、按需抽象结果、MVP、成功指标与待验证假设；完整模板另含埋点、风险和资源排期

> ROI使用限制：当前转换框架的成本量表为低成本高分，与分母的方向相反，尚需校准；暂不直接依据该分数决定优先级。此处仅统一公式说明，排序仍需综合战略、冲突、依赖和证据。

### 优先级排序框架

- **RICE打分法**：Reach × Impact × Confidence ÷ Effort
- **MoSCoW分类法**：Must / Should / Could / Won't
- **价值/复杂度矩阵**：四象限快速排序
- **排序输出模板**：标准化优先级表格
- **共用能力与依赖**：引用抽象结果，统一比较口径，避免收益和投入重复计算

## 🧠 B端 vs C端差异

| 维度 | B端侧重 | C端侧重 |
|---|---|---|
| 痛点判断 | 看ROI（能不能帮客户赚钱/省钱） | 看体验爽不爽 |
| 覆盖范围 | 大客户需求权重高 | 普通用户数量权重高 |
| MVP标准 | 能跑通核心业务流程就行 | 要够好用，不然用户直接不用 |
| 成功指标 | 效率提升、成本降低、转化率 | 留存、时长、NPS |
